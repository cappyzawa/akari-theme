# Theme model

This document defines the shared theme model: how a theme is declared, which
color roles every theme must assign, and what tool adapters may consume.
It is the contract between theme authors and adapter authors.

Status: the model is defined and illustrated by `themes/akari` and
`themes/ninja`. The loader reads theme directories, and every tool is
generated from them; the legacy palette route is gone. The engine is
named katazome.

## Pipeline

```text
themes/<id>/theme.toml + <variant>.toml
        |  parse, validate, resolve color expressions
        v
Resolved theme: metadata + one resolved variant per file
        |  adapters map roles to tool settings
        v
dist/<tool>/...
```

## Theme layout

A theme is a directory. Its final home is a repository of its own that
depends on the engine crate; until the engine is extracted, `themes/<id>/`
in this repository plays that role.

```text
<theme directory>/
  theme.toml        # identity, variant order, adapter metadata
  <variant.id>.toml # one self-contained file per variant
```

Each variant file is complete on its own. Variants do not inherit from the
theme or from each other. Sharing role expressions between variants can be
added later without invalidating files written this way.

### theme.toml

| Key | Required | Purpose |
|---|---|---|
| `theme.id` | yes | Machine identity: `[a-z][a-z0-9]*`. Used in file names, module namespaces, environment variables and palette names. |
| `theme.name` | yes | Display name, used in labels such as "Akari Night". |
| `theme.description` | yes | One-sentence description for manifests and file headers. |
| `theme.repository` | no | Source URL for manifests that publish it. |
| `theme.license` | no | SPDX identifier for manifests that publish it. |
| `theme.variants` | yes | Ordered list of variant ids. The first entry is the default variant for plugins that pick one. |
| `adapters.<tool>.*` | per adapter | Metadata one adapter needs to build a loadable artifact, such as a VS Code publisher. Each adapter documents its own required keys. Missing keys fail generation only when that adapter is selected. |

### Variant file

| Table | Values | Referenceable | Purpose |
|---|---|---|---|
| `[variant]` | strings | no | `id` (`[a-z][a-z0-9]*`), `name`, `appearance` (`dark` or `light`), `description`. |
| `[base]` | hex literals | yes | The two ground colors, `background` and `foreground`. Shared shape. |
| `[colors]` | hex literals, nestable | yes | Author-named pigments. Private to the theme. |
| `[ansi]`, `[ansi.bright]` | expressions | yes | The 16 terminal slots. Shared shape, resolved in two stages. |
| `[roles.*]` | expressions | no | Shared semantic roles. Consumers only. |

Adapters never read `colors`. Everything an adapter renders comes from
`variant`, `base`, `ansi`, `roles` and `theme.toml`.

## Expressions and resolution order

Expressions keep the existing syntax: a hex literal, a reference
(`base.background`, `colors.lantern.mid`, `ansi.bright.red`), or a nested
function call (`lighten`, `darken`, `brighten`, `mix`).
Resolution keeps the existing stages:

1. `ansi` may reference `base` and `colors`.
2. `ansi.bright` may also reference `ansi`.
3. `roles.*` may reference `base`, `colors` and `ansi` (including `ansi.bright`).

Roles cannot reference other roles. Two roles that should share a color
both reference the same source. The engine reports an unresolved or
forbidden reference instead of substituting a color.

## Role vocabulary

Every role below is required in every variant. There is no optional tier:
all bundled adapters are generated by default, so an unassigned role would
need a fallback, and fallbacks are outside this design.

A role names a purpose, not a color. Akari assigns one pigment to many of
them; a different theme may split them. Roles that pair a foreground with a
background stay separate so contrast remains under the author's control.

### `base`

| Role | Purpose |
|---|---|
| `base.background` | Default surface behind text. Literal. |
| `base.foreground` | Default text on the background. Literal. |

### `ui`: surfaces and interaction

| Role | Purpose |
|---|---|
| `ui.surface` | Status lines, panels, headers, slightly elevated from the background. |
| `ui.sunken` | Cursor line and other recessed strips. |
| `ui.raised` | Popups, menus, completion windows. |
| `ui.inset` | Side panels and bars set back from the editor. |
| `ui.border` | Window borders, separators, inactive borders, guide lines. |
| `ui.muted` | Secondary text: inactive tabs, faint labels, placeholders, globbing. |
| `ui.accent` | The primary highlight: focus borders, active borders, badges, buttons, progress, prompts, active line numbers. |
| `ui.accent_secondary` | A second highlight distinguishable from `ui.accent`: search-mode borders, secondary buttons, hover emphasis. |
| `ui.on_accent` | Text drawn over `ui.accent` or `ui.accent_secondary`. |
| `ui.selection_bg` | Selected text background. |
| `ui.selection_fg` | Selected text foreground. |
| `ui.match_bg` | Search match background. |
| `ui.cursor` | Cursor color. |
| `ui.cursor_text` | Text under the cursor. |
| `ui.active_bg` | Active window, tab or toolbar background. |
| `ui.link` | URLs and hyperlinks, in UI and in markup. |

### `diagnostic`

| Role | Purpose |
|---|---|
| `diagnostic.error` | Errors and failures. |
| `diagnostic.warning` | Warnings. |
| `diagnostic.info` | Informational messages. |
| `diagnostic.hint` | Hints and unobtrusive suggestions. |
| `diagnostic.success` | Success and completion states. |

### `diff`

| Role | Purpose |
|---|---|
| `diff.added` | Added lines and markers. |
| `diff.added_bg` | Background of added lines. |
| `diff.removed` | Removed lines and markers. |
| `diff.removed_bg` | Background of removed lines. |
| `diff.changed` | Modified lines and markers. |
| `diff.moved` | Moved code. |
| `diff.conflict` | Merge conflict markers. |
| `diff.ours` | The current side of a merge conflict. |
| `diff.theirs` | The incoming side of a merge conflict. |

### `syntax`

| Role | Purpose |
|---|---|
| `syntax.text` | Plain code text. |
| `syntax.comment` | Comments and documentation. |
| `syntax.keyword` | Keywords, control flow, storage modifiers. |
| `syntax.string` | String literals. |
| `syntax.character` | Character literals, distinct from strings. |
| `syntax.number` | Numeric literals. |
| `syntax.constant` | Named constants and enum members. |
| `syntax.type` | Types, classes, structs, interfaces, constructors. |
| `syntax.function` | Functions and methods. |
| `syntax.variable` | Variables and parameters. |
| `syntax.member` | Fields, properties, object keys. |
| `syntax.builtin` | Language builtins such as `self`, `this`, `super`. |
| `syntax.namespace` | Namespaces, modules, packages. |
| `syntax.attribute` | Attributes and HTML/XML attribute names. |
| `syntax.label` | Labels and lifetimes. |
| `syntax.tag` | Markup tags and selectors. |
| `syntax.punctuation_special` | Interpolation and template delimiters. |
| `syntax.decorator` | Decorators, annotations, special symbols. |
| `syntax.macro` | Macros and preprocessor directives. |
| `syntax.escape` | Escape sequences. |
| `syntax.regexp` | Regular expression literals. |
| `syntax.path` | File paths. |
| `syntax.directory` | Directory names in pickers. |

### `markup`

| Role | Purpose |
|---|---|
| `markup.heading_1` | Level 1 headings and titles. |
| `markup.heading_2` | Level 2 headings. |
| `markup.heading_3` | Level 3 headings. |
| `markup.heading_4` | Level 4 and deeper headings. |
| `markup.list` | List markers. |
| `markup.raw` | Inline code and code blocks. |

### `series`

| Role | Purpose |
|---|---|
| `series` | An array of exactly eight mutually distinguishable colors, in order. Used for bracket pair levels, chart series, collaborator cursors and rank badges. Adapters that need fewer take a prefix. |

### `ansi`

| Role | Purpose |
|---|---|
| `ansi.black` | Terminal slot 0. |
| `ansi.red` | Terminal slot 1. |
| `ansi.green` | Terminal slot 2. |
| `ansi.yellow` | Terminal slot 3. |
| `ansi.blue` | Terminal slot 4. |
| `ansi.magenta` | Terminal slot 5. |
| `ansi.cyan` | Terminal slot 6. |
| `ansi.white` | Terminal slot 7. |
| `ansi.bright.black` | Terminal slot 8, also line numbers and dim text. |
| `ansi.bright.red` | Terminal slot 9. |
| `ansi.bright.green` | Terminal slot 10. |
| `ansi.bright.yellow` | Terminal slot 11. |
| `ansi.bright.blue` | Terminal slot 12. |
| `ansi.bright.magenta` | Terminal slot 13. |
| `ansi.bright.cyan` | Terminal slot 14. |
| `ansi.bright.white` | Terminal slot 15. |

ANSI slots are explicit author choices. Adapters may consume them directly
for settings that a tool defines in terminal terms, such as `bright-green`
for raw markup in Helix, but must not derive them from syntax roles.

## Adapter contract

An adapter receives the theme metadata and one resolved variant at a time
(or all variants, for artifacts that bundle them).
It may read `theme.*`, `adapters.<tool>.*`, `variant.*`, `base.*`, `ansi.*`
and `roles.*`. It must not read `colors.*`.

Identity in artifacts derives from metadata, never from literals:

| Need | Source |
|---|---|
| File and directory names | `{theme.id}-{variant.id}` |
| Human labels | `{theme.name} {variant.name}` |
| Module namespaces, environment variables | `theme.id` (uppercased for variables) |
| Light or dark switches (`uiTheme`, `background`, `dark = true`) | `variant.appearance`, never `variant.id` |
| Default variant for plugins | first entry of `theme.variants` |
| Publisher, version, icon, repository | `adapters.<tool>.*` and `theme.*` |

## How the vocabulary was derived

The roles above come from an inventory of every template, copied Lua module
and the Terminal.app serializer, asking what each setting that referenced an
Akari pigment directly was for. The named colors were doing this work:

| Akari pigment | Purposes found |
|---|---|
| `lantern.mid` | keyword, character, tag, heading 1, strong emphasis, list marker, accent, cursor, warning, match, modified files, chart orange, series 1 |
| `lantern.far` | type, namespace, attribute, label, special punctuation, heading 2 and 4, changed lines, ours side, secondary accent, series 6 |
| `lantern.ember` | builtins (`self`, `this`, special variables and symbols), heading 3, some CSS values, series 8 |
| `life` | string, success, added lines, chart green, series 5 |
| `night` | member, info, theirs side, moved code, options text, chart blue, series 2 |
| `muted` | function, unknown rank, chart purple, Codex skill labels, series 3 |
| `rain` | exported only as a Starship named color |

Themes that export named colors to users (Starship palettes, zsh variables,
the Helix and Neovim palette tables) will export roles instead, because
adapters cannot name a theme's private pigments.

Roles that only a few adapters consume today: `ui.on_accent` (Helix, Neovim),
`syntax.character` (Helix, bat, Neovim), `diff.ours` and `diff.theirs`
(delta, VS Code), `series` (VS Code, Zed, Zellij, gh-dash, lazygit). They are
still required, for the reason given above.

## Akari settings to settle during migration

These are places where Akari's current templates disagree with each other.
The role assignment in `themes/akari` follows one side; the other side will
change output when its adapter migrates, and that change must be reviewed
rather than snapshot-refreshed.

- Modified files: VS Code and Zed use `lantern.mid`, Helix and `state.diff_changed` use `lantern.far`, but Dawn darkens `state.diff_changed` while Helix reads the pigment directly. `diff.changed` follows `state.diff_changed`, so Helix Dawn and the modified files of Zed and VS Code change.
- Added lines: Helix reads `ansi.green` directly while `state.diff_added` darkens `life` in Dawn. `diff.added` follows `state.diff_added`, so Helix Dawn changes, and so do VS Code's added and inserted colors, which read `life`.
- Hints: Helix reads `semantic.comment` while `state.hint` is a darkened `base.foreground` in Dawn. `diagnostic.hint` follows `state.hint`, so Helix Dawn changes.
- Series order: VS Code bracket levels and Zed collaborator cursors order the same pigments differently. `series` follows VS Code for the first six and appends Zed's remaining two, so Zed's order changes.
- Hint and predictive borders in Zed use `night` directly while `diagnostic.hint` is a lightened `night`; special strings in Zed use `lantern.far` while Helix and Neovim use `ansi.green`. Zed follows `diagnostic.hint` and `syntax.string`, so both change.
- Created files in Zed use `life` while `diff.added` darkens it in Dawn. They follow `diff.added`, so Zed Dawn changes.
- The hint status color in Zed reads `semantic.comment`. It follows `diagnostic.hint`, so Zed Dawn changes.
- The search match background in Zed is `lantern.mid` at 25% alpha while `ui.match_bg` is an opaque 20% mix. It follows `ui.match_bg`, so both Zed variants change.
- The new tab page link in Chrome uses `lantern.mid`. It follows `ui.link`, so both Chrome variants change.
- Zed reads ANSI slots directly for renamed files (`ansi.bright.cyan`), builtin functions (`ansi.bright.yellow`), link text and list markers (`ansi.cyan`). They map to `diff.moved`, `syntax.builtin`, `ui.link` and `markup.list` only if the color change is accepted.
- Codex's `skill` color has no role of its own. The Codex adapter uses `syntax.function`: a skill is a named capability the agent invokes, and the choice keeps Akari's `muted`.
- Merge conflict sides: delta uses `lantern.far` and `night`, VS Code uses `life` and `night`. `diff.ours` follows delta.
- Hover backgrounds in VS Code use `ansi.bright.yellow` directly; they map to `ui.accent_secondary` only if the color change is accepted. Decorators follow `syntax.decorator`, which Akari assigns the same slot.
- delta and Codex select dark or light output by testing `variant == "night"`; they must test `variant.appearance`.
- Marked base commit in lazygit: text over the `lantern.far` background uses `night`. The background is `ui.accent_secondary`, whose text role is `ui.on_accent`, so the text becomes `base.background` in both variants.
- Unstaged changes in lazygit use `ansi.red`. They mark modified files, so they follow `diff.changed` and turn amber.
- Author names in lazygit use `muted`. They are a collaborator color, and an adapter needing one series color takes the prefix, so they follow `series[0]` (`lantern.mid`).
- Rank icons in gh-dash use `life`, `night`, `lantern.far` twice and `lantern.mid` from newContributor to owner. They follow `series` from owner (`series[0]`) down to newContributor (`series[4]`), so owner and newContributor keep their colors and member, collaborator and contributor change. The unknown role is not a rank; it follows `ui.muted` instead of `muted`.
- The fzf marker uses `life` in the Nix attrset and the fzf template. The marker is a second highlight beside the `ui.accent` pointer, so it follows `ui.accent_secondary` (`lantern.far`) in both the Nix attrset and the fzf theme.
- Commands and aliases in zsh use `lantern.mid`. A command word is the callee of the line, as Neovim's `@function.call` treats it, so they follow `syntax.function` and turn `muted` like shell functions.
- Shell builtins in zsh use `lantern.mid`. They are language builtins, so they follow `syntax.builtin` and turn `lantern.ember`.
- Reserved words in zsh (`if`, `for`, `while`) use `night`. They are keywords, so they follow `syntax.keyword` and turn `lantern.mid`.
- Command options in zsh use `night`. An option is a parameter of the command, as Neovim's `@variable.parameter` treats flags, so options follow `syntax.variable` and turn `base.foreground`.
- Diff markup in bat: `Diff Changed` uses `lantern.mid` and `Diff Inserted` uses `life`. They follow `diff.changed` and `diff.added`, so bat's changed lines change in both variants and its inserted lines change in Dawn.
- JSON key levels in bat use `lantern.mid`, `lantern.far` and `life`. They take the first three `series` entries as nesting levels, like bracket pair levels, so levels 1 and 2+ change.
- Zellij multiplayer colors order `lantern.mid`, `life`, `night`, `muted`, `lantern.far`, then ANSI slots. Players 1 to 8 take `series` in order and players 9 and 10 keep `ansi.bright.green` and `ansi.bright.yellow`, so players 2 to 8 change.
- bat reads ANSI slots directly for builtin functions (`ansi.bright.magenta`), shell builtins and level 2 headings (`ansi.bright.yellow`) and list markers (`ansi.cyan`); Zellij's highlighted frame uses `ansi.bright.yellow`. They map to `syntax.builtin`, `markup.heading_2`, `markup.list` and `ui.accent_secondary` only if the color change is accepted.
- Search matches in VS Code use `lantern.mid` at 25% and 12% alpha. They follow `ui.match_bg`, opaque for the current match and at 50% alpha for the others, so both variants change.
- Input validation warnings in VS Code use `lantern.far`. They follow `diagnostic.warning`, so both variants change.
- JSON key levels in VS Code use `lantern.mid`, `lantern.far` twice and `life`. Like bat, they take the first four `series` entries, so levels 1 to 3+ change.
- Regular expression internals in VS Code use `muted` for character classes, `lantern.far` for class sets and `lantern.ember` for group punctuation. No role names them, so they follow `syntax.regexp` and all three change.
- Builtin tags in VS Code use `night`. They are tags, so they follow `syntax.tag` and turn `lantern.mid`.
- Changed text within a changed line (`DiffText`) in Neovim uses `lantern.mid`. It follows `diff.changed`, so both variants change.
- Level 3 and 5 headings in Neovim's legacy html and markdown groups use `lantern.mid`. They follow `markup.heading_3` and `markup.heading_4` like the treesitter levels, so both change. Levels 2, 4 and 6 there read `ansi.bright.yellow`; they map to `markup.heading_2` and `markup.heading_4` only if the color change is accepted.
- Neovim reads `ansi.black` for the backgrounds of floats, popup menus and folds (`ui.raised`), the cursor line and color column (`ui.sunken`), and the status and tab lines (`ui.surface`). In Dawn that slot is dark, so these strips are dark in the light variant. They map to those roles only if the color change is accepted.
- Neovim reads ANSI slots directly for window separators and float borders (`ansi.bright.black`), list markers and link text (`ansi.cyan`), builtin variables and functions (`ansi.bright.red`, `ansi.bright.magenta`), diff file headers (`ansi.bright.red`, `ansi.bright.green`), directories, HTML attributes and interfaces (`ansi.bright.cyan`), and heading levels 5 and 6 (`syntax.comment`, `ansi.blue`). They map to `ui.border`, `markup.list`, `ui.link`, `syntax.builtin`, `diff.removed` and `diff.added`, `syntax.directory`, `syntax.attribute`, `syntax.type` and `markup.heading_4` only if the color change is accepted.
- VS Code reads ANSI slots directly for level 2 headings (`ansi.bright.yellow`), renamed files (`ansi.bright.cyan`), link text, list markers and template keywords (`ansi.cyan`). They map to `markup.heading_2`, `diff.moved`, `ui.link`, `markup.list` and `syntax.keyword` only if the color change is accepted.
